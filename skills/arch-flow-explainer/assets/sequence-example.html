NICo bootstrap — how the three per-tray endpoints get learned

Sequence from operator pre-staging through DPU self-registration to steady-state lifecycle management.
The puzzle this solves: Each compute tray has three independent admin-net endpoints (host BMC, DPU BMC, DPU OOB), each on a separate piece of silicon with its own MAC and IP. NICo has to discover all three and figure out they belong to the same physical tray. Two endpoints are configured into existence by NICo's DHCP from a pre-staged inventory; the third self-registers via forge-scout; LLDP topology data is what stitches them together.
Pre-staging / scout DHCP / iPXE / Redfish (admin Ethernet) LLDP (in-band on the link) Self-registration / correlation Steady-state lifecycle

Numbered messages

1
Operator → NICo · import rack inventory
Operator loads the L11 factory inventory file: a list of MACs for every BMC and DPU in the rack (18 host BMCs + 18 DPU BMCs + 9 switch-tray BMCs per NVL72), plus the rack/slot labels.
2
NICo internal · prepare DHCP + DB
For each MAC, NICo creates a DHCP reservation in its DHCP service and an empty ManagedHost stub in Postgres. At this point NICo expects specific MACs at specific IPs but hasn't talked to any of them.
3
Host BMC → NICo · DHCPDISCOVER
BMC has standby power and comes up first. Sends a normal DHCP broadcast.
4
NICo → Host BMC · DHCPOFFER + ACK
MAC matches a reservation, so NICo hands out the pre-allocated IP (e.g. 10.10.2.71). The BMC now has its admin-net identity.
5
NICo → Host BMC · Redfish crawl
NICo immediately walks the Redfish tree to confirm hardware identity: serial, model, firmware versions, sensor inventory.
6
Host BMC → NICo · 200 OK
Redfish returns the inventory. NICo updates the Postgres row with serial, model, firmware. The host BMC endpoint is now known and verified.
7
(parallel) DPU BMC ⇄ NICo · same DHCP + Redfish flow
The DPU BMC is a separate MCU on the BlueField-3 card with its own MAC. It runs steps 3–6 in parallel and ends up at 10.10.2.72 with its own Redfish identity confirmed.
8
DPU → NICo · DHCPDISCOVER (PXEClient)
The DPU BMC has now powered up the DPU's Arm cores. UEFI on the DPU broadcasts DHCP with the PXEClient option set, indicating it wants to network-boot.
9
NICo → DPU · DHCPOFFER + iPXE URL
NICo replies with the DPU's reserved OOB IP (10.10.2.73) plus a next-server/boot-file pointing to an iPXE chain-load URL.
10
DPU → NICo · UEFI HTTP Boot
DPU UEFI fetches the iPXE script. The script then chain-loads the forge-scout init container image.
11
NICo → DPU · 200 OK + image
NICo serves the forge-scout image. The DPU loads it into RAM and starts executing — no persistent install yet.
12
DPU forge-scout → ToR · LLDP query
forge-scout reads LLDP frames the ToR is broadcasting on the mgmt-net link. This is in-band on that single Ethernet link, never crosses the wider network.
13
ToR → DPU · LLDP TLV
ToR identifies itself: chassis name (e.g. tor-rack2-leaf1) and port (e.g. Eth7). This is how forge-scout knows which physical port — and therefore which rack/slot — it's plugged into.
14
DPU forge-scout → NICo · gRPC RegisterDPU
The phone-home call. Payload: DPU MAC, OOB IP, LLDP neighbor, BlueField serial, board-level info. This is the DPU self-registering — unlike the BMCs, which were configured into existence.
15
NICo internal · correlation
The magic step. NICo looks up the LLDP neighbor in its topology database (tor-rack2-leaf1/Eth7 → rack 2, slot 7) and links the three independent admin IPs — host BMC, DPU BMC, DPU OOB — into a single ManagedHost row keyed on rack+slot.
16
NICo → DPU · push dpu-agent
forge-scout's job is done. NICo provisions the steady-state DOCA OS image with the dpu-agent daemon installed, and tells the DPU to reboot into it.
17
dpu-agent → NICo · long-lived gRPC
After reboot, dpu-agent opens a persistent gRPC connection back to NICo's API server and stays connected for the life of the host. NICo sends configuration through this channel; the agent reports status back.

Result: the ManagedHost row in Postgres

ManagedHost {
  rack:           2
  slot:           7
  serial:         SN-12345
  host_bmc_ip:    10.10.2.71   (mac aa:bb:cc:00:07:01)   ← DHCP-reserved (step 4)
  dpu_bmc_ip:     10.10.2.72   (mac aa:bb:cc:00:07:02)   ← DHCP-reserved (step 7)
  dpu_oob_ip:     10.10.2.73   (mac aa:bb:cc:00:07:03)   ← self-registered (step 14)
  lldp_neighbor:  tor-rack2-leaf1 / Eth7                  ← discovered via forge-scout
  state:          READY
  dpu_agent:      connected
}
