NICo call flows — multi-rack deployment (one rack shown)

Same architecture as the single-rack diagram, but call counts and aggregation behaviour reflect a real N-rack site.
Reading this diagram: Only one rack is drawn for clarity. Each flow is labelled with how it scales — site-wide means one connection total, ×N means one per rack, ×18N means one per compute tray across all racks. The ×N other racks placeholder on the right indicates where the same in-rack stack repeats.
Control plane (admin Ethernet) Bootstrap / discovery Telemetry (mTLS REST) In-band, never on mgmt network

Numbered call flows — multi-rack scale

1
NICo → NMX-C · gRPC ×N
One gRPC session per rack — to that rack's NMX-C VIP. NMX-C is the per-rack aggregator, so NICo doesn't fan out to individual switch trays.
2
NICo → BMC · Redfish HTTPS ×18N
Unicast Redfish per compute tray. For 4 racks that's 72 BMC sessions; for 40 racks it's 720. No BMC aggregator.
3
NICo → dpu-agent · gRPC / DOCA ×18N
Steady-state lifecycle ops per DPU. dpu-agent on each DPU holds an outbound gRPC connection back to NICo.
4
NICo → SDN Controller · gRPC / REST site-wide
Tenant VPC intent. NICo declares "VPC X spans DPUs in racks 1, 3, 7" and the SDN Controller decides what to push where.
5
SDN Controller → DOCA SDN agent · DOCA SDN ×18N
Programs VXLAN VNIs and ACLs on every DPU that's part of a tenant. Cross-rack tenants are tunnelled DPU-to-DPU over the underlay.
6
SDN Controller → FRR (ToR) · NetQ Edit / NETCONF ×2N
Configures BGP-EVPN underlay on every ToR, and the spine session if managed. Spine routers carry the inter-rack VXLAN transit.
7
NMX-M → NMX-C and NMX-T · mTLS REST ×N
One pull session per rack to each of NMX-C and NMX-T. This is where NMX-M genuinely earns its keep — single-rack you can poll directly, multi-rack you need aggregation.
8
DHCP/iPXE → DPU · DHCP + UEFI HTTP Boot ad-hoc
Per-DPU on first power-on. Same DHCP service handles boot scopes for all racks; admin subnets must be routable to it from every rack.
9
forge-scout → NICo · gRPC callback ad-hoc
Per-DPU during ingestion. forge-scout reports LLDP neighbour info → NICo infers which rack/slot the DPU is in.
10
NMX-C → NVSwitches · in-band NVLink
Programs LIDs and forwarding tables. Stays inside the rack; one independent control plane per rack.
11
NVSwitch ↔ GPU · in-band NVLink data plane
Scale-up at 1.8 TB/s, bounded by the rack. Multi-rack tenants get one NVLink partition per rack.
12
NICo → UFM · gRPC / REST site-wide
InfiniBand tenant isolation. NICo asks UFM to assign a PKey covering the tenant's GPUs across whichever racks they live in. UFM is genuinely needed for multi-rack.
13
UFM → IB switches · in-band IB management
UFM programs PKeys, routing, and SHARP trees on the Quantum-X800 fabric. The IB control plane is separate from Ethernet — runs over its own management partition.
14
ConnectX HCA ↔ IB fabric · in-band IB data plane
Inter-rack GPU scale-out. When a tenant spans racks, this is what carries the cross-rack collectives — NVLink can't.
